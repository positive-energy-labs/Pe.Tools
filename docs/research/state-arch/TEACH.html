State for routes — what the bake-off taught

For kaitpw, 2026-08-24. Use: decide the substrate for every route and every chat plugin, then cut /takeoffs over. All code below is verbatim from the worktrees; paths under each block. Deep dives: 08-synthesis.md, READING-GUIDE.md.

0. The one sentence

A route is one importable object that owns a dependency graph. URL bindings are leaves, host reads are async nodes that track their parents across await, feeds are pure projections, and writes name what they invalidate. React only subscribes.

Every candidate could do the "one object, zero useState in panes" part — that was discipline, not library. Only one primitive did the bolded part. That is the whole verdict.

1. The pattern you liked, and its one flaw

qr-repo's asyncCompute: a signal that holds an AsyncState, recomputed by an effect when its inputs change, with an AbortController to drop stale runs.

function asyncCompute<T>(cb: () => Promise<T>) {
  const loading = new AsyncLoading<T>();
  const s = signal<AsyncState<T>>(loading);
  const c = computed<Promise<T>>(cb);          // ← tracking happens HERE, synchronously
  let controller: AbortController | null;

  function execute(cb: Promise<T>, cancel: AbortSignal) {
    s.value = loading;
    new Promise<T>((resolve, reject) => { /* race cb against cancel */ })
      .then((result) => { s.value = new AsyncData<T>(result); })
      .catch((error) => { s.value = error === reset ? loading : new AsyncError<T>(error); });
  }
  effect(() => {
    if (controller != null) controller.abort(reset);
    controller = new AbortController();
    execute(c.value, controller.signal);
  });
  return s;
}

W1. computed(cb) tracks only what cb reads before its first await. Here this.units.value is read after await awaitAsync(...), so changing units does not recompute. The shape is right — a node that owns its own loading/error/data and cancels itself — but the tracking primitive is synchronous. This is the flaw every candidate was measured against.

3. Feeds: one projector, six words

The library gives AsyncResult (Initial | Success{waiting} | Failure). Users and agents read FeedState. Exactly one function crosses that line, so "stale" means the same thing on every route.

export type FeedState =
  "live" | "fresh" | "stale" | "loading" | "error" | "fixture";

export interface Feed {
  options: Option[] | null;   // null = legal-options SEAM
  state: FeedState;
  at?: number;                // when read
  basis?: readonly string[];  // exact input tuple of that read
  note?: string;
}
export function resultFeed<A>(result, options, fixture, live = false): TakeoffFeed {
  if (AsyncResult.isInitial(result))
    return { options: null, state: "loading", note: "not read yet" };
  if (AsyncResult.isFailure(result))
    return { options: null, state: "error", note: String(Cause.squash(result.cause)) };
  if (!result.value.bound)
    return { options: null, state: fixture ? "fixture" : "fresh",
             note: "unbound; no host read", basis: result.value.basis };
  return {
    options: options(result.value.value),
    state: result.waiting ? "stale" : fixture ? "fixture" : live ? "live" : "fresh",
    at: result.value.at, basis: result.value.basis,
  };
}

7. The two decisions you didn't understand

G7 — who owns the visible row order

The atlas table (TanStack Table) filters and sorts rows. Keyboard next/prev and "select all visible" need that order. Today the table component computes it during render and writes it back into the store:

onVisibleChange={(keys) =>
  (visibleKeys.length !== keys.length || visibleKeys.some((key, i) => key !== keys[i])) &&
  store.actions.setAtlasPage({ visibleKeys: keys })      // render → store write → re-render
}

takeoff/atlas.tsx:1124–1128; AtlasPageState.visibleKeys at store.ts:157

That is census smell S2 (derived state copied into a store) wearing a new coat: the store holds a value it cannot compute, fed by a component effect. Two honest options:

Rule to carry: if a store field can only be written by a component, it is not state — it is a derived value in the wrong place.

G8 — one registry per app, or one per store?

An AtomRegistry is the graph instance: values, subscriptions, TTL. The cutover does AtomRegistry.make() inside createTakeoffStore (store.ts:297) — your instinct. Two facts weigh against it:

  1. The Suspense hook keys promises by atom only, in a module-global Map (@effect/atom-react/dist/Hooks.js:221): if the same atom object is read through two registries they share one promise; if a store is disposed mid-read the entry leaks. Per-store atoms avoid the collision but not the leak.
  2. Your chat plugins already need one shared graph. workbench/route-state.tsx:134 keeps route docs in an Atom.family keyed {route, stateKey, scope}, and the comment says why: "shares one wire across every inline card and dock for the same coordinate." A route is on screen 3–4 times at once (N inline cards + dock + sentence + the route's own iframe). A per-store registry would give each mount its own copy of the host reads.
Recommendation: keep the per-route store object (namespace, actions, inspect(), fixture seam) but make it a handle over the one app registry, passed in like the host: createTakeoffStore({ host, sessions, search, registry }). Atoms stay per-store-instance; families that must dedupe across mounts (route docs, host reads) key on (route, scope) exactly like route-state.tsx already does. Write it as an ADR; the cost is one constructor arg and deleting line 297.

8. Chat plugins — what I missed, and what it changes

Retraction (2026-08-25): A shared browser registry cannot unify iframe, dock, and server realms; the route document is the source and each store subscribes, as ruled in w1-demiurge.md §3a.

Not considered in the bake-off. Reading it now (workbench/route-chat-plugins.tsx, ADR 0001):

  • A plugin is { spec: RouteStateSpec, Renderer }; the same spec drives the pea MCP tool, the runtime workspace, and the web card. Route identity is the URL segment. Good — that is the S1 "Product" noun already living server-side.
  • State reaches a plugin through useRouteState(spec) → Effect atom family → SSE. Writes go out-of-band (writeRouteState POST) and come back only via SSE. This is already substrate B, minus the shape: no feeds, no basis, no declared invalidation, and scope re-derived from window.location.search on every write (route-state.tsx:20–24) — so a chat-side card and the iframe of the same route read two different documents (workspace vs thread scope).
  • The dock unmounts on every turn start and remounts at agent_end, so plugin useState dies each turn — S7 (zero useState in panes) is not a style preference here, it is the only way plugin UI survives a turn.
  • Design-system ledger 243–246 already names the gap: /takeoffs and /families keep all state inside the React tree, so no plugin can read them.

So the substrate question was already answered by the plugin system; the cutover's job is to give it the shape: route store = RouteStateSpec + atoms in the shared registry, keyed by (route, scope); the route page, the inline card, the dock and the sentence are four panes of one store. That collapses "make every route a plugin" into "every route is a store; a plugin is a pane".

9. Apply it (transfer check)

Answer these against /families or /runs before we cut anything else:

  1. Name its waterfall as a → b → c. Which step reads something after an await that could change independently? (That's where W1 would have bitten.)
  2. Which of its writes should invalidate which keys? If you can't list the keys, the route has an S15 loop somewhere today.
  3. Which of its component-local values would a chat card need to show? Those are the fields that belong in the store, and nothing else.
  4. For G7: is there any store field on that route that only a component can compute?
