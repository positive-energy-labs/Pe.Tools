# Headless documents in interactive Revit

Question (kaitpw, 2026-09-26): can agents work on Revit documents in the background, with no window, no tabs, no person in the loop? What can such a document do, what breaks, how fast, how stable? And what does that mean for cloning centrals for tests and periodic backups?

Three independent axes, each chosen separately:

| Axis | Values | Decided by |
|---|---|---|
| window | **windowed** or **headless** | `UIApplication.OpenAndActivateDocument` vs `Application.OpenDocumentFile` |
| central | **central**, **local**, **detached** | `OpenOptions.DetachFromCentralOption` on a workshared file |
| process | **foreground** (a person's Revit) or **background** (an agent's Revit) | which `Revit.exe` holds the document |

A **headless document** has no `UIDocument` window: `GetOpenUIViews()` is 0, `Document.ActiveView` and `UIApplication.ActiveUIDocument` are null, and Revit shows Home when no document has a window. The SDK's `doc open --detach` already opens this way (`pe.revit.sdk` `BridgeApplication.cs:447-451`), because `DetachFromCentralOption` exists only on the non-activating overload. Design Automation opens every document this way (`Pe.Dev.RevitAutomation.Worker/RevitAutomationShellApp.cs`, an `IExternalDBApplication`).

Evidence: `.artifacts/runs/session-20260926-headless/{census,capability,capability2,capability3,stability,falsify,round4}/REPORT.md` (gitignored; the verdicts are here). Sessions: `roomsdev1` (rooms-dev-loop worktree payload, pid 57936, crashed 01:24), `headless1` (main 20c1464a, pid 37364, crashed 02:17, restarted as 51596), `headless2` (snapshot, pid 5244, the adversary lane). Model: the Duryee clone, 223 MB, 112k elements, a workshared local opened detached. A claim without a lane is testimony.

## Works on a headless document (PROVEN[session])
- Reads: document and view-scoped collectors on plans never opened in a window (`FEC(doc, view.Id) = 213 in 154 ms`), `CropBox`, `GetPlanViewRange`, `get_BoundingBox(view)` clipped to the view, geometry with `Options{View=plan}`, `SpatialElementGeometryCalculator`.
- Writes: lines, walls, rooms, parameter sets, deletes, `Regenerate`, `TransactionGroup.Assimilate`, rollback; ~0.4 s for four walls, a room, a regenerate and a commit on 112k elements. The rooms partition created and deleted ~1100 elements on this clone.
- Failures: a per-transaction `IFailuresPreprocessor` that deletes warnings commits with no dialog (115 ms); an error with `SetClearAfterRollback(true)` rolls back with no dialog; an `Application.FailuresProcessing` handler that deletes warnings lets an open with 122 posted warnings succeed with zero dialog lines in the journal.
- Exports: `ExportImage` of never-opened plans, sections and a temporary isometric (created and rolled back in one script); DWG (1.1 s); PDF of a plan (2.7 s) and a nine-view sheet (3.5 s) via `Document.Export(PDFExportOptions)`; `ViewSchedule.Export` (0.2 s).
- Save: a detach-and-preserve copy accepts only `WorksharingSaveAsOptions{SaveAsCentral=true}` (53 s) and becomes a live central with `_backup` and `.slog`; reopening it headless opens the central itself, not a local. A detach-and-discard copy accepts only plain `SaveAs` (56 s) and reopens as a standalone non-workshared file with no sidecars. `doc.Save()` after a commit: 4.9 s.
- Worksets: `WorksetConfigurationOption.CloseAllWorksets` on a detach-preserve open cuts open time 25.4 s → 19.4 s, keeps every element enumerable, and skips loading the cloud IFC link.
- Transmission: `TransmissionData.ReadTransmissionData` works on a closed file (6 references; the cloud IFC link is absent from it). `WriteTransmissionData` with `IsTransmitted=true` works headless on a copy, and every later API open of that copy comes back detached automatically, no dialog, no `_backup`.
- Scripts: `scripting.execute` binds to a headless document's openId whether the SDK or a script opened it; the Pe.Tools bridge tracker lists both (`isActive:false`). `doc current --json` lists it too; only the plain-text output says "No active document".
- Background service: Revit unfocused, minimized, or on Home with only a headless document open serviced 6 to 12 requests each with no input, script start 2.4–5.1 s after request; the latency is pea startup and compile. The stall seen earlier on `roomsdev1` was a host restart plus bridge reconnect, not Home.
- Open time: headless is faster than windowed by 5–20% (alternated runs, Snowdon Architectural, medians 26.3 s vs 31.3 s with two Revits running; 12.5 vs 13.9 s with one). Close ~1.1 s. Ten cycles of one model hold memory flat.
- Opens that raise no dialog: a 2023 file (upgraded in memory), a workshared local without detach, `Audit=true` (+60% time), the central itself with default options (opens in place, no local created). `OpenDocumentFile` on a path already loaded as a link returns a second wrapper over the link document in 3 ms (`Equals` true, `ReferenceEquals` false) that cannot be closed and dies with its host. A file saved by a later Revit throws `CorruptModelException`.

## Fails, refuses, or differs (PROVEN[session] unless marked)
- Print: `PrintManager.SubmitPrint` to "Microsoft Print to PDF" blocks on a Windows "Save Print Output As" dialog (`PORTPROMPT:`) that `DialogBoxShowing` never sees; the script sat 300 s until the window was closed from outside; the print-to-file name persisted after rollback. Banned headless; `Document.Export(PDFExportOptions)` is the path.
- Activation: `RequestViewChange` on a headless document throws `InvalidOperationException: Changing the active view is not applicable to inactive documents`. But `OpenAndActivateDocument(path)` on an already-open headless document gives it a window in place, keeping its openId (the SDK's `doc close` swap does exactly this). Same `Document` object: UNPROVEN. And `OpenAndActivateDocument(modelPath, OpenOptions{DetachAndPreserveWorksets}, false)` is accepted (windowed detached document, 33 s), so the SDK comment at `BridgeApplication.cs:384-387` that detach needs the non-activating overload is wrong.
- Cloud: Revit itself refuses `DetachFromCentralOption` on a cloud path in 15 ms, no dialog (`ArgumentException: Detach option is not valid for cloud model`).
- Borrowing is not transactional: `WorksharingUtils.CheckoutElements` inside a transaction reaches central at once and the element stays owned after rollback; only `RelinquishOwnership` returns it. A headless open of the central afterwards showed zero owned elements.
- Detach is not isolation: a detached open of a local still writes a full session into central's `.slog` (`>Open:Local`, file grew 1081116 → 1082850 B). A detached document cannot sync (`SynchronizeWithCentral` throws "This Document does not have a central location"; `ReloadLatest` throws "not a local model").
- Links: `LoadFrom` on an absolute path on another user's machine throws `FileArgumentNotFoundException`; a cloud (Forma) link has no file path type; neither travels with a copy.
- Identity: `PathName` is the bare file name; `GetWorksharingCentralModelPath()` returns an empty path.
- Pe.Tools host ops behind `RequireDocumentUi` (`RevitDataRequestService.cs:1292`) refuse a document that is not active: `revit.apply.command.execute`, `revit.matrix.schedule-profiles`, `revit.detail.sheets`, `revit.catalog.parameter-evidence`, `revit.detail.electrical-panel-schedules`, `family.open`, `revit.glance.attention`, `revit.context.summary`, `revit.resolve.references`, `revit.context.visible-summary`, `revit.context.view-rendering-state`, and scoped branches of `revit.detail.schedules`, `revit.matrix.schedule-coverage`, `revit.matrix.parameter-coverage`, `revit.detail.elements`. Pure-DB ops (`rooms.*`, `takeoffs.*`, most `revit.catalog.*`, `schedule.*`, `family.capture|plan|apply`) are headless-safe. `revit.context.view-image` is listed under the guard yet exported on the headless clone: verify the branch.
- Not Design Automation: DA has no RevitAPIUI (no `DialogBoxShowing`, a dialog hangs the job), loads only your bundle, and runs one process per job. Interactive Revit loads third-party add-ins (`ConsoleApp` threw from Idling 1713 times in one journal) and accumulates memory across models.

## Hazards for a background design
1. **Modal dialogs reach the screen.** A headless open that posts warnings, or one commit warning, raises `Dialog_Revit_DocWarnDialog` on whoever owns that Revit; kaitpw's Cancel aborted an open. `DialogBoxShowing` + `OverrideResult` closes the dialog but always rolls the transaction back, for every result code, and returns `True` even for nonexistent codes, so its return value proves nothing; `SetForcedModalHandling(false)` and `SetDelayedMiniWarnings(true)` do not stop it. Only failure ownership keeps control: `FailuresProcessing` at application level or an `IFailuresPreprocessor` per transaction. Judge dialog outcomes from the journal. PROVEN[headless1 P06b, capability2 P02, headless2 F04]
2. **A native fault kills the process and every document in it.** `FilteredElementCollector(doc, viewId, linkInstanceId).WhereElementIsNotElementType()` on the Duryee clone died with `AccessViolationException` (Application log 1026, same coreclr offset) four times on four Revits: headless with the link hidden in the view, headless with it visible, and **windowed** with the local opened normally. Not headless-specific, not about hidden links. The one run that survived (capability P04c) had first run a plain view collector and an image export on that view; the crashing runs touched the view for the first time with the link collector. UNPROVEN whether a plain view collector first makes it safe. A collector on the link's own `GetLinkDocument()` is safe. .NET cannot catch it, and the first crash took a person's unsaved clone. PROVEN[roomsdev1 P04d; headless1 P07b, P07c, P07w]
3. **A crash poisons the shared host.** The crashed script's action stays `unknown`; `POST /actions/recover` fails because the SDK liveness check reads the dead pid as `Win32 error 31`, within a minute of the crash and long after; the journal persists on disk (`%LOCALAPPDATA%\Positive Energy\Pe.Tools\state\host\<service>\partition-operations.json`) so a host restart does not clear it; `ts/apps/host/src/action-journal.ts:320-347` lets one `unknown` action refuse every new action on the host, for every session on it. Round4 cleared it by hand-editing the action to `failed`. Revit relaunches the host itself when it stops. Per-agent Revits do not help while they share a host.
4. **Opening a path already loaded as a link returns the link document**, not an independent one; it becomes `InvalidObjectException` when its host closes. Open order changes link reloads, which is what posted the 122 warnings.
5. **Memory builds across different models** and does not level off in 8 cycles (private bytes 2562 → 2807 MB); working set is not evidence (Windows trims it). A long-lived background Revit needs a budget and recycle.
6. **Two trackers disagree** about a script-opened detached document: the Pe.Tools bridge has the right title and an openId; the SDK's `doc current` shows the pre-detach title, no openId, and the link as a separate document. `scripting.execute` needs a windowed anchor document to accept a request.
7. **Bridge and CLI versions drift**: CLI beta.163 against a deployed bridge beta.161, so `doc borrows` and the at-stop borrow check return 404 (`session.borrows-unrecorded`).
8. All evidence came from sessions without `--quarantine`. UNPROVEN whether a quarantined agent Revit behaves differently.

## Files on disk (worksharing plumbing)
Beside a file-based central there are exactly the central `.rvt`, one local `Name_<user>.rvt` per person who opened it normally, and a `_backup` folder plus `.slog` for each. There is no `_detached.rvt` unless someone saves a detached copy (`_detached` is an in-memory title). Opening the central through the API with default options opens the central in place and creates no local. PROVEN[filesystem; headless2 F09b]

"Controls Plan - Level 2" exports all white headless and windowed alike, byte-identical PNGs (md5 `afc6897a…`); Mechanical Zoning Plan Level 1 and 2 are byte-identical both ways too. The view holds nothing that draws (section boxes, circuits, a camera, a link contributing one element; its template hides ducts, fixtures and grids). Not a headless defect. ## What `doc clone` is and is not (`BridgeApplication.cs:518-585`)
It opens with `DetachAndDiscardWorksets` (:565-566), `SaveAs` (:569-570) with link and transmission paths untouched, subscribes `DialogBoxShowing` only (:534-535) with no `FailuresProcessing` (unlike `doc open`, :423-432), always ends windowed via `OpenAndActivateDocument(output)` (:573), and for cloud first opens connected with no conflict callback (:541-561). It is a standalone-file maker, not a backup primitive.

## Implications for pe.revit.sdk (to muse, not decided)
- Isolation is a process and a host, not a detach flag: agent Revits in their own process and their own host journal, `--quarantine`, a memory budget and recycle, and a host that blocks only the destination with an `unknown` action.
- Failure ownership everywhere the SDK opens or writes: `FailuresProcessing` plus a per-transaction preprocessor, extended to `doc clone` and to documents scripts open; `SubmitPrint` banned; a guard on view-plus-link collectors; dialog outcomes read from the journal.
- A real backup verb: choose preserve or discard worksets, `SaveAsCentral` or plain, `CloseAllWorksets` for speed, transmitted-copy for a file that always opens detached, and an honest report of links that do not travel (foreign absolute paths, cloud links).
- One document census that does not depend on `ActiveUIDocument`, with openIds for script-opened documents.
- Liveness must count a missing pid as dead; bridge and CLI versions must be pinned together.
- Document-first open (kaitpw, 2026-09-26): the document is the only thing a caller should have to name. The year comes from the file (`source/Pe.Revit.Versioning/RevitFileInfo.cs:47-71` already reads it without Revit, unused by `doc open`); the document opens in the newest live session of that year, `--id` and `--year` override; with permission, a session of that year starts when none exists. Today `SessionCommand.Resolve` (`SessionCommand.cs:922-944`) ignores year and refuses on zero or several live sessions. The SDK session ledger rejects silent inference twice (custody, cloud conflict policy); a year the file states is not inference, and the permission gate keeps the auto-start inside that rule. First class in the web UI and the CLI alike. Home for the ruling: `pe.revit.sdk/docs/features/session/LEDGER.md`.
