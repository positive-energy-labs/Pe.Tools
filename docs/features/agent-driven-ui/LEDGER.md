# agent-driven-ui ledger

Pea and a human co-editing known-schema route state — the agent mutates a semi-persistent, schema'd artifact through tools/MCP; the human edits the same artifact concurrently and approves before anything reaches Revit.

## Decided

- 2026-07-06 — The question is **collaborative UI**, not generative UI: the agent does not invent UI, it writes known-schema state through tools. Write paths must include in-app Pea, external MCP agents (Claude, scripts), and eventually browser-native agents. The requirement decomposes into four layers — artifact (persistence) · write paths (tools) · reactivity (fan-out) · approval — and no single library covers all four.
- 2026-07-06 — Define each route's collaborative surface ONCE (a zod-schema'd "route toolset": artifact schema + `{name, description, inputSchema, execute}` tools) and project it through three doors: mastra `clientTools` for in-app Pea, `MCPServer` tools + resource subscriptions for external agents, WebMCP `document.modelContext.registerTool` when it matures. The projection functions are thin; this shared surface is the library-agnostic asset. Every framework evaluated is one *door* to it, not the surface itself. Spec: [COLLABORATIVE-UI.md](COLLABORATIVE-UI.md).
- 2026-07-06 — **Do not adopt CopilotKit or re-adopt ag-ui.** The load-bearing core is already ours: `WorkbenchState` + `WorkbenchEvent` (event-sourced single store), first-class tool calls, approvals, and a `WorkbenchProvenance` type that already carries `protocol: "ag-ui"`. Every framework's value concentrates in the store / shared-state / approval columns — exactly where we already ship a working implementation. None of them ship a data grid or field-level provenance; those are ours regardless.
- 2026-07-06 — **The grid must not live inside assistant-ui.** `ExternalStoreRuntime` is message-list-shaped by contract. Chat stays a pure projection (`workbenchToThreadMessages`); the grid is its own TanStack-backed component beside it. An in-chat "confirm batch" tool UI may *reflect* grid state, never own it.
- 2026-07-06 — **Proposals, not merges.** The agent never writes committed state; it writes a separate `proposals` map keyed by cell, fed by one new `fill_state_updated` WorkbenchEvent (JSON-Patch). Co-editing conflict is *avoided, not resolved*: a human edit to a cell with a pending proposal marks that proposal `stale`. No timestamps race, no lost edits, no CRDT, no shared-state last-write-wins.
- 2026-07-06 — Approval is **accept-with-modified-value**: approve → optimistic TanStack commit; edit → approve with a corrected `resumeData` (edit is not a side channel); reject → `bail()`/decline. Reuse `WorkbenchApprovalRequest` + mastra `sendToolApproval`/`resumeStream` — mastra's storage-backed, restart-safe HITL is the strongest version in the field and is already our backend. Steal CopilotKit's render-and-wait *UX shape*, not its runtime. Push-to-Revit gates on committed cells only.
- 2026-07-06 — Live fill uses mastra's native structured-output stream (`agent.stream({ structuredOutput })` → `object` chunks, AI-SDK `useObject` semantics) applied to the per-route slice. No new dependency. Design fork worth knowing: cell-by-cell partials are not schema-validated mid-stream, while array/element streaming gives validated whole rows without mid-cell granularity — pick per surface.
- 2026-07-06 — Per-cell provenance streams **inline in the schema**: each cell is `{ value, page, bbox, confidence }` rather than a scalar. Costs tokens, zero plumbing; out-of-band data parts + index correlation is the alternative and is not worth the wiring yet.
- 2026-07-06 — Artifact home splits by scope: mastra working memory (`scope: 'resource'`, deep-merge `updateWorkingMemory`, `useStateSignals` deltas) for per-user collaborative state; a first-class artifact table + JSON-Patch log on the pe server for artifacts shared across users and bound to a Revit model — which also supplies the audit trail engineers need.
- 2026-07-06 — Multi-client fan-out is the one genuinely missing piece in every option evaluated (mastra has no post-stream push, CopilotKit's state channel is run-scoped, MCP notifies only MCP clients). It belongs on our existing SSE wire as a `WorkbenchEvent` broadcast — the same discipline that keeps assistant-ui a projection.

## Tried & rejected

- 2026-07-06 — Framing the requirement as "stream structured output into an audit grid": the wrong question. Structured-output streaming is one fill mechanism; it gives no write path to external agents, no persistence, and no shared artifact. Corrected to tool-driven collaborative UI the same round.
- 2026-07-06 — CopilotKit on this stack, re-scored fairly (it *is* built for this loop, and `@ag-ui/mastra`'s `registerCopilotKit` integration is real): it covers only the in-app door. It does not cover persistence (state is run/session-scoped), the external-MCP door, WebMCP, or multi-tab fan-out — all of which force building the artifact layer anyway, at which point its remaining surface is duplicative UX packaging plus a second state channel running parallel to `WorkbenchState`. Revisit only if maintaining the in-app door becomes a burden.
- 2026-07-06 — ag-ui's RFC-6902 wire, subscriber pattern, and AbstractAgent/HttpAgent client: the shared-state *idea* (`STATE_DELTA` as JSON-Patch) is good and worth stealing as one `WorkbenchEvent` variant; the dependency is not.
- 2026-07-06 — CopilotKit `useCoAgentStateRender` for live fill: its mid-node emission mechanism is LangGraph-Python-shaped, a poor fit for a mastra backend, and it renders in-chat rather than in a side grid.
- 2026-07-06 — WebMCP as a bet today: W3C draft (Feb 2026), Chrome 149 origin trial, discovery/invocation partly TODO, consumers are Gemini-in-Chrome and an inspector extension. Watch it; the shared toolset shape means zero rework when it matures.

## Owed

- Build the three-door surface. Spike proving all four layers (~1–2 days, spec in [COLLABORATIVE-UI.md](COLLABORATIVE-UI.md) §"Suggested spike"): `defineRouteToolset` + `toAgentClientTools` (~100 lines) → a lab route where Pea fills a schedule via `set_cell` clientTool calls staged as proposals → working memory with `useStateSignals` → `MCPServer` mounted with the same toolset, driven from Claude Code, with one elicitation approval and SSE fan-out to a second tab. **Nothing from this spike exists in our source yet** (no `fill_state_updated`, no route toolset, no mounted `MCPServer`).
- Spike field-level extraction citations against the current hand-built estimator — the highest-leverage buy in the stack, and it is on the extraction side, not the UI side. `estimate.ts` reconstructs cell geometry from raw LlamaParse because LlamaParse grounds *blocks*, not *fields*; LlamaExtract (`cite_sources`, XYWH px + confidence scores), Reducto (`generate_citations`, normalized 0–1), and Extend (`citationsEnabled`, polygons + split logprob/OCR confidence, and it grounds *computed* values) all return `{page, bbox, confidence}` per field natively. Run the Enphase/ACME sheets through LlamaExtract and Reducto and compare against the estimator. (Full comparison table in git history: `docs/features/agent-driven-ui/RESEARCH.md`, deleted 2026-08-17.)
- Confidence-threshold auto-routing (Extend's pattern): auto-accept high-confidence cells, flag low-confidence for review.
- Buy-triggers to re-open the build-vs-buy question, none currently true: 3+ heterogeneous agent backends behind one UI (ag-ui's normalization earns its weight); wanting CopilotKit's managed cloud tier; standardizing the backend on LangGraph.
