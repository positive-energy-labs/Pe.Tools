# Transcript tool results and action receipts

## Scope and proof

This report reviews source only at commit `527048f09530a30fbf46e567908c17c8f4118563` on 2026-09-16. It does not run a server, a test, Revit, or `pe-revit`.

Claim under review: the `receipts` Reading can reconstruct every tool-call shape that the web transcript renders after large results are removed from `/pe/thread/:id`.

Verdict: **FALSIFIED[source review]**. `readThreadState` returns the messages from `controller.queryThreadMessages` without a second result store (`source/pe-tools/packages/runtime/src/thread-state.ts:29-50`). The `receipts` Reading returns `ActionJournal` rows for admitted actions only (`source/pe-tools/apps/host/src/resource-adapters.ts:112-123`). Many rendered calls have no action row, and an action row does not contain the complete transcript wrapper.

## Fields that the web reads

`selectToolCalls` derives one `ToolCall` from stored `tool-invocation` parts and live `activeTools`. The UI contract contains `id`, `title`, `args`, optional `target`, optional `parentMessageId`, `images`, `status`, optional `result`, and failure `error` (`source/pe-tools/apps/web/src/workbench/chat-state.ts:61-76`). Stored calls supply `rawInput ?? args`, `result`, error state and error text; live calls can instead supply `shellOutput`, `partialResult`, and progress images (`source/pe-tools/apps/web/src/workbench/chat-state.ts:94-163`).

The receipt frame is itself conditional transcript content. Route plug-ins extract an action ID from the result's nested `action.id`, the result's `id`, or `args.input.actionId` (`source/pe-tools/apps/web/src/workbench/route-chat-plugins/receipt-id.ts:7-17`). Mutating `op:` and `pod:` calls then mount `ActionReceiptView`, while action-oriented route plug-ins show either that frame or “This call has no admitted action receipt” (`source/pe-tools/apps/web/src/workbench/route-chat-plugins/tool-names.tsx:161-190`, `source/pe-tools/apps/web/src/workbench/route-chat-plugins/tool-names.tsx:399-414`). `ActionReceiptView` performs `{ kind: "receipts", id }` and renders the action row's state and operation result (`source/pe-tools/apps/web/src/actions/receipt.tsx:22-57`, `source/pe-tools/apps/web/src/actions/receipt.tsx:135-152`).

## What one receipt contains

`receipts` with an `id` observes `journal.list(target, id)` and returns the full row. A list without `id` is reduced to `ActionStatus`; the `id` form is not reduced (`source/pe-tools/apps/host/src/resource-adapters.ts:112-123`). `ActionJournal.list` filters persisted rows by exact document lifetime and/or action ID (`source/pe-tools/apps/host/src/action-journal.ts:95-107`).

Each action ID stores:

- Identity and intent: `id`, `kind` (`operation` or `workflow`), action `key`, `actor`, execution `destination`, inner action `request`, and `bases` (`source/pe-tools/packages/agent-contracts/src/action-receipts.ts:43-51`).
- Execution history: `steps`, with each step's `id`, `key`, `kind`, `input`, state, and either `result` or failure fields; `preparation`; recovery evidence; publication state/result; and `startedAt` (`source/pe-tools/packages/agent-contracts/src/action-receipts.ts:5-61`).
- Terminal action data: succeeded `result`; failed/unknown `error`, `status`, optional `nativeOutcome`, `issues`, and evidence; or incomplete `error`, `status`, and `result` (`source/pe-tools/packages/agent-contracts/src/action-receipts.ts:63-80`). `ActionJournal` copies the admission into the row and later records step results, publication results, and the final result (`source/pe-tools/apps/host/src/action-journal.ts:200-223`, `source/pe-tools/apps/host/src/action-journal.ts:284-324`).

This is an action contract, not a transcript contract. It has no assistant message ID, tool name, full `pe_do` args, Scope revision, live partial result, shell output, synthesized UI error, or approval payload. Its `destination` can recover an admitted execution target, but it is not the transcript result's `{ target: { session, document }, revision }` wrapper.

## Which calls have receipts

Pea exposes `pe_find`, `pe_read`, `pe_do`, `target_set`, `capture_view`, `read_image`, `diagram`, `request_access`, `revit_api_docs_search`, and `revit_api_docs_fetch` (`source/pe-tools/packages/mcps/src/pea/index.ts:48-79`). Only an admitted external action creates an `ActionJournal` row:

- A mutating `op:` dispatched by `pe_do` uses the tool-call ID as `requestId`; `HostRpcCaller` submits an `ActionAdmission` and returns the action row alongside the response (`source/pe-tools/packages/mcps/src/pea/capability-tools.ts:315-331`, `source/pe-tools/packages/mcps/src/pea/capability-tools.ts:341-361`, `source/pe-tools/packages/mcps/src/shared/host-rpc-caller.ts:185-255`).
- A `workflow:` semantic action uses `input.actionId` when supplied, otherwise the tool-call ID, and returns the action row as its inner result (`source/pe-tools/packages/mcps/src/pea/capability-tools.ts:393-416`).
- A mutating `pod:` uses the tool-call ID for the admitted `scripting.execute` operation (`source/pe-tools/packages/mcps/src/pea/capability-tools.ts:502-542`).
- `pe_do` refusals, read-only operations, action-control reads, schedule/family reads, route document reads/writes, and route commands do not universally admit a row keyed by the tool-call ID; their dispatch paths return direct data or route results (`source/pe-tools/packages/mcps/src/pea/capability-tools.ts:279-335`, `source/pe-tools/packages/mcps/src/pea/capability-tools.ts:363-451`, `source/pe-tools/packages/mcps/src/pea/capability-tools.ts:544-595`).
- `pe_find`, `pe_read` of non-mutating rows or skills, `target_set`, media tools, docs tools, `diagram`, `request_access`, and the runtime `ask_user` suspension do not enter `ActionJournal`. For example, `diagram` only validates args and returns counts (`source/pe-tools/packages/mcps/src/shared/diagram.ts:4-20`).

| `target_set`, docs search/fetch, access request, and other direct tool results | Transcript and trace JSON | **No.** These tools are in the product tool set but have no `ActionJournal` admission path (`source/pe-tools/packages/mcps/src/pea/index.ts:56-79`). |

## Conclusion

1. Elision behind `receipts` cannot reconstruct every tool-result shape rendered today.
2. It can recover full `ActionReceipt` rows for admitted host operations and workflows when the transcript retains or can derive the action ID.
3. It cannot recover direct Pea-tool results, read-only results, route results, diagrams, media/progress payloads, validation failures, or approval questions.
4. Even for admitted actions, it cannot reconstruct the complete transcript wrapper, including Scope `revision`, displayed resolved `target`, full tool args, synthesized error, and parent message association.
5. Universal elision therefore needs a transcript-owned lazy result source keyed by `threadId` and `callId`, such as `GET /pe/thread/:id/part/:callId`; `receipts` can remain the action-detail source for calls that expose an action ID.
