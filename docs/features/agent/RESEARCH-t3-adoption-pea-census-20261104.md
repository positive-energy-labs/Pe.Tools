# T3 adoption: Pea source census

Date: 2026-11-04. Pe.Tools HEAD: `be0e94dcb8ea73e13e3684e911a0fb30772a652d`. The working tree already had unrelated changes. This report is the only file written for this census.

## Question and boundary

The requested decision is whether T3 Code can replace Pea's agent bedrock, and which product responsibilities must survive. Source-observed: Pea already delegates the model loop to Claude or Codex via ACP while the host owns product thread records and integration ([TS guidance](../../../ts/AGENTS.md), [philosophy](PHILOSOPHY.md)). This is therefore a bedrock and integration replacement, not evidence that the Pea product can be discarded. T3's embedding API, distribution rights, persistence, authentication, and feature parity were not inspected. **UNPROVEN**: feasibility, migration cost, runtime behavior, and any actual LOC deletion. All classifications below are proposed boundaries inferred from source, not an implementation verdict. No code or Revit was executed.

## Source scope, not a savings estimate

PowerShell recursively selected `.ts` and `.tsx` under the named source directories, excluded filenames containing `.test.`, and used `Get-Content | Measure-Object -Line` (nonblank lines, including comments; no generated-code classification). Snapshot: host harness 6 files / 3,988 lines; agent-contracts 87 / 14,921; runtime 11 / 1,596; MCPs 40 / 7,203; web workbench 39 / 5,218. These are overlapping functional neighborhoods, not a complete dependency closure and not deletable LOC. Fixtures or generated material may remain; tests outside these directories are excluded. `threads.ts` in particular mixes transport with persistent product responsibilities. Product LOC delta from this research: zero.

## Decision gates

1. **UNPROVEN**: T3 can be embedded and redistributed in Pea, expose its events and controls, support required providers and endpoints, and accept Pea tools with caller identity. Inspect its actual supported integration contract before estimating replacement.
2. **UNPROVEN**: a bridge preserves existing thread history, resumability, Work links, permissions, questions, cancellation, consent, receipts and forks across restart and migration. Specify and exercise those behaviors on the appropriate lanes before cutover.
3. **UNPROVEN**: Pods, Autodesk authentication, local-only startup, and user-facing sharing survive a replacement. These are independent product obligations, not consequences of a successful model turn.
