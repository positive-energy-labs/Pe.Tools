# T3 Code adoption: core and history

Research date: 2026-11-04. Source-only inspection of `pingdotgg/t3code`. No runtime, package installation, or Pea integration was exercised.

## Recommendation

Do not replace Pea's ACP/contracts and UI wiring with T3 as a library today. Investigate a pinned source integration or upstream collaboration as a bounded spike, not a dependency commitment. T3 has meaningful reusable provider interfaces and a shared client runtime, but its packages are private and its orchestration and MCP services live in the server application. This evidence does not establish an SDK release plan or timeline. The alternative, running T3 as a separate product, is a different integration and was not tested.

Falsify this recommendation with an external consumer outside the monorepo that installs supported versioned packages, creates a provider session, persists and resumes a thread, exercises cancellation and MCP delegation, and drives a custom UI without importing `apps/server` or copying its internals. Also prove Pea's host operations, consent, cancellation, and event ownership against that consumer. Ask upstream for a supported contract and release policy before relying on one. Until those checks pass, any replacement cost or compatibility claim is a projection.

## Seams and coupling at HEAD

- [ProviderAdapter](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/packages/provider-core/src/server/ProviderAdapter.ts#L595-L697) defines a session runtime, event stream, turn start and adapter session creation. [ProviderDriver](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/packages/provider-core/src/server/driver.ts#L25-L52) couples a provider instance to the orchestration adapter; [ProviderHost](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/packages/provider-core/src/server/ProviderHost.ts#L15-L55) supplies host services. The adapter imports T3 contracts and uses Effect schemas and streams. These are real internal seams, not evidence of stable third-party API compatibility.
- [runtimeLayer](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/orchestration-v2/runtimeLayer.ts#L60-L94) composes infrastructure and stores; its [production layer](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/orchestration-v2/runtimeLayer.ts#L357-L380) is in the application. The [MCP service](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/mcp/OrchestratorMcpService.ts#L155-L219) and [delegation implementation](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/mcp/OrchestratorMcpService.ts#L2346-L2356) are also app code. [MCP HTTP server](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/mcp/McpHttpServer.ts#L824) names `delegate_task`; [remote delegation](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/server/src/peer/RemoteDelegation.ts#L64) describes linked-environment delegation. These T3 tools originate in T3 server code; this does not establish that all tools displayed in a thread originate there, since provider tools also exist.
- [Web dependencies](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/web/package.json#L34-L36) directly use workspace client-runtime, contracts and provider-core; [app initialization](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/apps/web/src/appInit.tsx#L1-L2) imports both runtime and contracts. Separation exists, but this is shared product wiring and does not demonstrate a framework-neutral drop-in UI. ACP itself remains present in [provider-acp](https://github.com/pingdotgg/t3code/blob/e68e19d605485db6ef31b2033f67a9d07634fc2b/packages/provider-acp/package.json#L2-L27); adopting T3 does not inherently remove ACP.

## Direction and counterevidence

[9eea28bacd](https://github.com/pingdotgg/t3code/commit/9eea28bacd) added provider-core and provider-testing on 2026-10-08 14:18:16 -07:00. [9b0df1358f](https://github.com/pingdotgg/t3code/commit/9b0df1358f) moved Pi into a provider package one second later; [e62161bc5b](https://github.com/pingdotgg/t3code/commit/e62161bc5b) moved OpenCode on October 8. [2c1915b319](https://github.com/pingdotgg/t3code/commit/2c1915b319) exposed model metadata through a port and [784b5625f9](https://github.com/pingdotgg/t3code/commit/784b5625f9) placed MCP provider sessions in a service on October 9. This is evidence of increasing modularity and potential extraction, not a promise to publish.

Against an inference that an SDK is imminent: all three censuses retain private packages; the app still owns the runtime composition and delegation; and [06e627448b](https://github.com/pingdotgg/t3code/commit/06e627448b) and [2f85686d9d](https://github.com/pingdotgg/t3code/commit/2f85686d9d) show MCP tools evolving around explicit product targets and caller access. [6049196c50](https://github.com/pingdotgg/t3code/commit/6049196c50) fixes provider switching and background work on November 3, illustrating continuing runtime development, not proving instability in any particular external use. The source cannot establish the maintainers' future plans.
