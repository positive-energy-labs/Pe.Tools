- 2026-09-18 (ruling-ff-coercion; supersedes the "formula refusal aborts the transfer", R1-R3 and "instance formula not carried to type" lines): a migration is the user's declared old→new mapping with a `mappingStrategy` each, and the engine carries values across data type, unit spec, storage type and scope. The user: "always map it, differing revit units should ideally never be a gate for a mapping except in the very very very few places where following the users intent would cause bad side effects", and on instance→type "the users declaration wins". A source formula that cannot cross (`FamilyFormulaCopy.Blocker`: never across data types, R1 "require units for every number"; or Revit refuses it, such as a type destination reading an instance parameter) is dropped with a note on plan, receipt and log, and each type's value is carried by the strategy. Only a value the strategy cannot carry refuses (`value-not-coercible`), naming value and type. A half-written transfer rolls back whole. Proof: compile and Shared.Tests; attached hold owed.
- 2026-09-18 (ruling-ff-coercion): units cross a mapping only through an explicit unit, never the project's display units. Two measurable specs convert through a unit both accept (`CoerceByStorageType.SharedUnit`); text into a measurable spec parses only when it names its unit (`TryParseExplicitMeasure`); different dimensions and bare numbers refuse that value. `CoerceElectrical` reads bare numbers in a fixed unit per spec. A mapped destination of another data type steps aside as its own first source instead of refusing.
- 2026-09-19 (user: "always map, and always be careful of implicit units bc project units are a bitch and hidden"; supersedes "bare numbers refuse that value" above): a mapping may declare `mappingUnit` beside `mappingStrategy`, one of `MappingUnits` for the destination spec; a bare number (Number, Integer, unit-less text) crosses through it, never the project's display units. With none declared, the value is not guessed and the family is not refused: `MissingUnitException` leaves it uncarried, its source is kept with its values (`NormalizeParamSources.Kept`), and preview and receipt name family, type, source, value and the declaration (`declare mappingUnit on '<dest>' (a unit of <leaf>, e.g. "Btu/h")`). A re-run with mappingUnit fills the destination's blank types and removes the source. A unit of another spec refuses at parse, or at plan when only the shared definition knows the spec (`mapping-unit-not-of-spec`). Scope (user, 2026-09-19: "ff that operates on families is different by nature than schedules that operates on projects. they can scope unit resolution differently."): Family Foundry resolves units inside the family document from the declared mappingUnit only; schedules and parameter writes resolve from the project field's display-unit evidence (schedule-grid LEDGER, Owed). Two resolvers, one rule (never guess); do not merge them.
- 2026-09-19 (user ruling on the instance→type question, option a): an instance→type mapping carries each type's stored value; a formula a type parameter cannot hold is dropped, its evaluated per-type values written and the drop reported (`FamilyFormulaCopy.DroppedNote`), never a family refusal.
